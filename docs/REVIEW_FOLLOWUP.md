# Freeze code-review: закрыто и принято осознанно (финальный гейт G37)

## Исправлено в этом проходе (review-фиксы)

1. **HIGH — `webhooks.py`**: `GRANTING_EVENTS` сокращён до `transaction.completed`.
   Раньше `subscription.updated` / `subscription.activated` при каждом пинге Paddle
   создавали заказ и продлевали подписку заново — дни накручивались бесплатно.
   Теперь доступ открывает только событие, где реально прошли деньги.
2. **MEDIUM — `comms.mark_target`**: Условие `AND status='claiming'` — после
   reclaim (>600 с) опоздавшая отметка первого `run()` не засчитывается и не
   задваивает `broadcasts.sent`; целевую статистику пишет только владелец заявки.
3. **MEDIUM — `users.extend_subscription`**: чтение `sub_until` + расчёт + UPDATE
   в одной транзакции — параллельные оплаты одной клиентки накапливают дни
   (не last-writer-wins).
4. **MEDIUM — `users.touch`**: `_touch_tasks` — сильная ссылка на фоновую задачу
   last_seen (GC не убьёт запись до записи).

## Принято осознанно (не блокеры запуска)

- **Cross-process free-limit** (`limits.user_lock` — только в процессе): бот и API
  — два процесса; две задачи/устройства юзера могут пробить бесплатный недельный
  лимит на пару сообщений. Деньги не задеты: entitlements и кристаллы атомарны в
  БД (guard в UPDATE/единая транзакция). Текёт только бесплатный лимит, чинится
  атомарным счётчиком в БД — отдельная задача.
- **`frame-ancestors 'self'` + X-Frame-Options SAMEORIGIN** блокируют Mini App в
  iframe веб-клиента Telegram. Ограничение существовало и до сессии
  (SAMEORIGIN). Слабить безопасность ради web.telegram.org решили не стали:
  Mini App рассчитан на нативные клиенты.
- Мелочи LOW (ретрай 4xx в `telegram.py`, атомарный `mark_order_paid` через
  rowcount, дубликаты фактов памяти при параллельной экстракции) — оставляем в
  порядке рефакторинга; деградация незаметна при 10k.
