# ТЗ: Продакшен «Оракул» под 10 000+ пользователей

> Дата: 2026-08-03. Статус: черновик для исполнения.
> Цель: выпустить продукт в продакшен без багов и ошибок при **внезапном наплыве 10 000
> пользователей** в день запуска, и устойчиво работать дальше.
> Принцип: работаем как одна команда — инженерия, QA, DevOps, бизнес-аналитика,
> маркетинг, дизайн, SEO, юриспруденция. Каждая роль закрывает свою волну, общая
> цель одна: запуск без поломок.

## 0. Резюме

«Оракул» — Telegram-бот (aiogram) + Mini App (FastAPI) + админ-панель: личный
AI-астролог с 6 агентами, 13 скиллами, натальной картой (Swiss Ephemeris), Таро,
Матрицей Судьбы, практиками, дневником, гороскопами по 12 знакам, монетизацией
(Stars + Paddle + Кристаллы), двухуровневой рефералкой и PDF-разборами для
маркетплейсов.

**Что уже сделано и подтверждено:**
- 219 тестов зелёные (pytest), selfcheck проходит без ошибок;
- инженерный аудит разложен на 28 целей **G1–G28** (`.omc/ultragoal/goals.json`),
  из них 3 готовы (зелёный CI, боевой шаблон `.env`, убрана БД из git);
- боевой `.env.production.example` собран;
- docker-compose: бот + API + Caddy(https) + ежедневный бэкап.

**Что осталось до запуска — 4 блока:**

4. **Бизнес/маркетинг/дизайн/SEO/право** — юнит-экономика, запуск, контент,

## 2. Целевые показатели (SLO) под 10 000 пользователей

Согласованные критерии, по которым будем считать систему готовой к запуску.

| Метрика | Цель |
|---|---|
| Ответ бота на вопрос | p95 < 10 с, p99 < 30 с (включая LLM-цепочку и фолбэк) |
| API (Mini App) | p95 < 400 мс, p99 < 1,5 с (кроме генераций) |
| Ошибки 5xx | < 0,1% запросов; ноль ошибок в денежных путях |
| Аптайм | 99,5% в месяц (без учёта плановых релизов) |
| Утренний прогноз | до 09:30 по локальному времени пользователя |
| Рассылки | каждый таргет ровно один раз; все доставлены за час от слота |
| LLM-бюджет | себестоимость на активного пользователя в день ≤ заданного лимита (см. юнит-экономику) |
| Целостность денег | повторная доставка платежа/вебхука НИКОГДА не выдаёт товар дважды; краш между шагами оплаты не теряет покупку |
| Бэкапы | ежедневные, off-site, восстановление проверено (RTO < 4 ч) |
| Масштаб | пик 10 000 юзеров/сутки, до 4 000 DAU, до 2 000 одновременных в чате — без деградации |

**Оценка нагрузки (прикидка для нагрузочного теста):**
- 10 000 установившихся → ~3 500–4 000 DAU, ~1 000–2 000 в день задают вопросы;
- ~8–12 тыс. LLM-вызовов/сутки (вопросы + фоновая память/прогнозы) — с учётом G23,
  цель снизить реальный объём в 3–4 раза;
- утренний пик: 3–4 тыс. персональных прогнозов в окно 08:00–09:30 по таймзонам;
- API: пиковый RPS ~20–50, чтение статики Mini App каждым открытием.

## 4. Инженерия (технический долг до продакшена)

План детально расписан в `.omc/ultragoal/brief.md` (28 целей). Здесь — сводка по волнам
и жёсткий порядок: **сначала деньги и гонки, потом LLM под нагрузкой, потом рассылки
и БД, затем API/Telegram, деплой, желательные улучшения, тесты.**

### Волна A — Фундамент: зелёный CI + боевой конфиг ✅ (готово)
G1 тесты зелёные, G2 selfcheck exit0 + `.env.production.example`, G3 БД убрана из git.

### Волна B — Деньги: целостность платежей (P0)
- **G4** Атомарная оплата→выдача: `apply_payment`/`redeem_promo`/`pay_with_crystals`
  сейчас делают `mark_order_paid` и `_apply_grant` в разных транзакциях — краш между
  ними = «заплатил, товара нет» навсегда. Выдача в ту же транзакцию (или
  `paid_pending_grant` + reconciliation).
- **G5** Гонка `users.ensure` при двойном `/start` → `IntegrityError` → 500.
  `INSERT OR IGNORE` + повторный `get`.
- **G20** Гонка реферального бонуса: проверка «первой оплаты» до вставки → бонус
  может начислиться дважды. Проверку внутрь транзакции.

### Волна C — LLM под нагрузкой (P0)
- **G6** Семафор + bucket-лимитер + circuit breaker на `app/core/llm.py`; экспоненциальный
  бэкофф с `Retry-After`. Сейчас сотни корутин бьют в API без ограничения → 429-шторм.
- **G7** Таймауты 180 с → 30–40 с + общий бюджет времени на запрос (фолбэк по бюджету).
  Сейчас фолбэк-цепочка при мёртвом провайдере занимает до ~18 минут.
- **G8** Параллельная генерация утренних прогнозов (семафор 20–30 корутин, предгенерация
  ночью, офлайн-шаблон при перегрузке). Сейчас тик на 5 000 аудитории идёт ~4 часа.
- **G23** Снизить реальный LLM-объём в 3–4×: не экстрактить память на короткие ответы,
  батчить, кешировать recall. Это и стоимость, и скорость.

### Волна D — Рассылки (P0)
- **G9** Один запуск рассылки: `broadcast_loop` (бот) и `broadcast.tick` (планировщик)
  зовут `run()` без in-flight-блокировки → дубли. Атомарный клейм таргетов
  (`UPDATE…RETURNING`) или per-broadcast `asyncio.Lock`.
- **G10** Голодание хвоста: `LIMIT 5000` без `ORDER BY` → при >5000 в одной таймзоне
  часть пользователей НИКОГДА не получает прогноз. `ORDER BY tg_id` + курсор/батчи.

### Волна E — Слой данных (P0)
- **G11** Сериализовать миграции на старте (`BEGIN IMMEDIATE`/файловый lock) — иначе
  бот и API, стартующие вместе, падают на втором `ALTER`.
- **G12** `transaction()`: ловить `BaseException` (иначе `CancelledError` оставляет
  частичную запись, которую коммитит чужой транзакцией).
- **G13** Недостающие индексы: `payments(order_id)`, `promo_redemptions(code,tg_id)`,
  `referrals(invitee_id,level)`, `events(created_at)`, `llm_usage(created_at)`; DAU/WAU
  переписать на `day>=?`.
- **G14** Ретеншен событий (purge 90–180 дн) + аналитика и `last_seen` не в hot-path.
- **G15** Память без полных сканов: SQL-фильтр + кеш recall.

### Волна F — API и Telegram (P1)
- **G16** `share.py`: Pillow в `asyncio.to_thread` (не блокировать event loop).
- **G17** Rate-limit `/api/horoscope` + атомарная проверка кеша.
- **G18** Общий rate-limiter исходящих Telegram + ретрай `createInvoiceLink`.
- **G19** Гонка лимита на бесплатном плане: атомарный счётчик / per-user lock.
- **G22** Зафиксировать решение по in-process лимитеру `_hits`: 1 воркер API, Redis при росте.

### Волна G — Деплой и мониторинг (P1)
- **G21** Healthcheck бота + off-site бэкап (S3/другой VPS). Локального бэкапа мало для ПДн.

### Волна H — Желательные улучшения (P2)
- **G24** CSP + rate-limit на ~40 админ-эндпоинтов.
- **G25** Cache-control для статики Mini App/админки (каждое открытие рефетчит ~186 КБ).
- **G26** Мелкие фиксы: опечатка «Ом Сom» в мантре, мёртвый `backfill_embeddings`,
  двойная сборка гороскопов.
- **G27** Зависимости: aiosqlite, `PRAGMA wal_autocheckpoint=2000`, локдаун версий,

### Волна I — Покрытие тестами (P1)

## 6. DevOps / SRE: мониторинг, бэкапы, CI/CD

### 6.1 Мониторинг и алертинг
- **Sentry** (Python): ловит все необработанные исключения бота и API. Это первое,
  что включить — без него «багов нет» просто не видно.
- **Healthchecks**: у API уже есть `/api/health`; добавить healthcheck бота (G21) —
  зависший поллинг перезапускается сам.
- **Алерты** (UptimeRobot или Telegram-уведомления из бота):
  - падение процесса bot/api (контейнер перезапущен, алерт);
  - рост 5xx > 1% за 5 минут;
  - backlog рассылок > N (рассылка застряла);
  - LLM: доля фолбэков/офлайна > порога, средняя латентность;
  - диск > 80%, размер бэкапов.

> **Сделано (G31):** Sentry подключён в оба процесса (`app/core/sentry.py`,
> включается из `SENTRY_DSN`, 500-обёртка middleware шлёт исключение в Sentry);
> UptimeRobot мониторит внешний `https://домен/api/health`, а compose-healthcheck
> бота (`scripts/healthcheck.py`) и API перезапускают зависший контейнер сам.
- **Логи**: `docker logs` уже с ротацией (json-file 10m×5). При росте — централизованный
  сбор (Sentry + docker logs достаточно для старта).

### 6.2 Бэкапы (P0 для ПДн)
- локальный `.backup` ежедневно уже есть (docker-compose, 14 дней);
- **off-site**: выгрузка бэкапа в S3-совместимое хранилище / на второй VPS (G21);
- **проверка восстановления**: раз в месяц восстановить бэкап в пустой БД, прогнать
  `PRAGMA integrity_check` + selfcheck. Непроверенный бэкап — это отсутствие бэкапа.

### 6.3 CI/CD
- GitHub Actions (G27): lint (ruff), pytest + selfcheck на каждый PR, сборка Docker,
  метки на теги → деплой на VPS по SSH.
- **Staging**: отдельный инстанс (та же compose) с тестовым ботом-дубликатом и
  DEV_MODE=1. На нём — ручной тест-план и нагрузочные прогоны.
- **Релизная дисциплина**: заморозка деплоев за 48 ч до запуска; деплой в рабочий день
  утром; откат = `docker compose` на предыдущий образ (образы тегаются).

### 6.4 Инфраструктурные решения (зафиксировать)
- **Ровно 1 воркер API** (`--workers 1` в compose, G22). Причины: (а) rate-limiter
  запросов `deps._hits` живёт в памяти процесса — несколько воркеров дадут каждому
  свой запас; (б) бакет исходящих Telegram (`app/core/flood.py`) тоже in-process —
  два воркера вдвое превысят номинальный темп. Поэтому лимитеры in-process, а
  не Redis: их синхронизация появится вместе с переходом на много воркеров.
- SQLite WAL на одном VPS держит 10k — ок. При росте до 30–50k (или первых
  двух воркерах API) — переход на PostgreSQL с репликой + Redis-лимитеры
  (схема описана переносимо, меняется только `app/data/session.py` и тип id).
- VPS: 2–4 CPU, 4 ГБ RAM, SSD. Caddy сам выпускает https.

## 8. Маркетинг: запуск и каналы

### 8.1 Позиционирование
«Личный AI-астролог 24/7, который **помнит тебя** и делает **настоящие расчёты**».
Ключевое отличие от конкурентов-«болталок»: карта считается по Swiss Ephemeris,
Таро — честный случай, модель не выдумывает числа. Это главный маркетинговый козырь.

### 8.2 Каналы привлечения (по убыванию отдачи для бюджета ≈ 0)
1. **Каналы-спутники с гороскопами** (уже в коде, флаг `horoscope_channels` выкл):
   12 каналов по знакам + автопостинг. Это бесплатный ежедневный трафик и SEO-подпитка.
2. **Рефералка 2 уровня** (уже в коде): бонус за оплату, а не за регистрацию —
   антинакрутка. Сделать реферальный оффер заметным в профиле.
3. **PDF-разборы на маркетплейсах** (уже в коде): товар + «золотой билет»-промокод.
   Запустить листинги до дня X (Etsy, местные площадки).
4. **Инфлюенсеры-астрологи/эзотерические блогеры**: бартер на промокоды-билеты —
   CAC почти 0.
5. **Органика/SEO**: лендинг + контент (волна SEO).

### 8.3 Запуск (день X)
- **Предзапуск (за 7–14 дней)**: тезисы, тизер в каналах-спутниках, предзапись
  «приглашение на запуск», раздача промокодов блогерам.
- **День X**: публикация в каналах-спутниках, пост инфлюенсера, рассылка по своей базе.
  Ожидаемый наплыв 10k — он и есть цель нагрузочной подготовки.
- **День X+1..X+3**: следить за конверсией и себестоимостью, оперативно гасить жалобы
  (Sentry + поддержка), НЕ менять цены и механики без данных.

### 8.4 Контент и копирайтинг
- Проверить и дошлифовать все тексты онбординга, лимитов, возврата (часть в
  `seed.py CONTENT`); tone of voice — тёплый, «мистический», без манипуляций.
- Контент-план каналов-спутников: ежедневные гороскопы + еженедельные обзоры лунного
  цикла + призыв «спросить Оракула» (C2A).
- Кейсы/отзывы (с согласия): «мне Оракул подсказал...» — соцдоказательство.

## 11. Юридический / комплаенс

### 11.1 Персональные данные (ПДн) — P0
- Бот собирает дату/место рождения, имя, переписку, память — это чувствительные ПДн.
- **Политика конфиденциальности** на лендинге + ссылка в онбординге и на Mini App:
  что собираем, зачем, где хранится (VPS), как удалить (`/delete_me` уже есть —
  анонимизация, финансовый след остаётся).
- **Удаление данных**: проверить, что `/delete_me` анонимизирует все персональные поля
  (не только user) — память, дневник, сообщения, гео-данные, карту.
- Ограничение доступа к БД: бэкапы шифрованы / в защищённом хранилище.
- Для РФ — соответствие 152-ФЗ (уведомление, согласие); для ЕС — GDPR (если аудитория
  в ЕС: право на забвение). Настроить согласие при онбординге.

### 11.2 Оферта и возвраты
- **Публичная оферта** / условия использования: описание тарифов, автоматическое
  продление, порядок возвратов (Telegram Stars — через поддержку Telegram; Paddle —
  через Paddle).
- Механика возвратов: уведомить поддержку; в админке есть «выдача из админки» — добавить
  при необходимости статус refunded (в схеме есть `payments.status=refunded`).

### 11.3 Дисклеймеры (частично есть)
- «Оракул создан для самопознания... не заменяет врача, психолога и юриста» — уже в
  `settings.disclaimer`; показать в онбординге и/или в FAQ.
- Астрологические заявления не должны выглядеть как гарантии (особенно деньги/здоровье).
- Возраст 18+ или 16+: зафиксировать и упомянуть в оферте.

### 11.4 Кризисный протокол
- Уже реализован и покрыт тестами (`safety.py`, G-проверки в selfcheck): суицид,
  самоповреждение, насилие не доходят до модели, выдаются контакты помощи.
- Проверить, что контакты локальны (уже есть `safety.helplines` для РФ/КЗ/БУ/УА).

G9, G10 (рассылки) → G11, G12, G13 (БД) → G19. После каждого шага: selfcheck + pytest.
Параллельно DevOps ставит Sentry и off-site бэкап (G21).

**Неделя 2 — Инженерия P1 + QA.** G14–G18, G22–G27 (CI), G28 (тесты). После G28 —
нагрузочный тест 10k, тест-план на гонки. Параллельно БА считает юнит-экономику,
юрист готовит политику и оферту, дизайнер аудирует онбординг, маркетолог готовит
каналы и контент, SEO — лендинг.

**Неделя 3 — Качество и полировка.** Ручной тест-план на staging, фиксы по QA,
полировка UX, листинги PDF, запуск каналов-спутников на тест. Финальный прогон
selfcheck + pytest на staging и на боевом.

**Неделя 4 — Запуск.** Предзапусковая заморозка (48 ч), чек-лист предзапуска,
день X по runbook, день X+1..3 — наблюдение.

> Этапы можно совмещать (роли параллельны), но **P0-инженерия — критический путь**:
> без G4–G13, G19, G20 запуск недопустим.

## 14. Runbook дня запуска (наплыв 10k)

1. **За 48 ч**: заморозка деплоев. Проверить конфиг на боевом: `DEV_MODE=0`,
   `BOT_TOKEN`, `ADMIN_ID`, `WEBAPP_URL=https://домен`, LLM-ключи, `PADDLE_WEBHOOK_SECRET`
   (если включаем). `selfcheck` на сервере — все ✅.
2. **За 24 ч**: staging-прогон ручного тест-плана; тестовая оплата Stars и Paddle;
   тестовая рассылка на себя; бэкап БД проверен восстановлением.
3. **За 2 ч**: включить мониторинг (Sentry, алерты), проверить логи, снять снапшот
   размеров БД.
4. **День X**: запуск маркетинга по плану. Наблюдение:
   - Sentry: растут ли ошибки (фикс/откат по протоколу);
   - планировщик: уложился ли утренний тик (SLO 09:30), размер backlog рассылок;
   - LLM: доля фолбэков, себестоимость, 429 от провайдера;
   - БД: размер, `database is locked` в логах, время healthcheck.
5. **При проблеме**: уведомить в админ-чат, применять откат на предыдущий образ
   (тегированный), НЕ держать систему в полурабочем состоянии. Проблема → задача в
   бэклог → фикс после стабилизации наплыва.

## 15. Definition of Done (критерии готовности к продакшену)
