# Операции и эксплуатация

Как проект живёт на сервере: деплой, мониторинг, бэкапы, запуск и масштабирование. Для DevOps/админов.

## Состав и принципы

Процессов ровно два — **бот** и **API**, это принципиальное решение:

- Планировщик, утренние прогнозы, рассылки и автопостинг гороскопов живут **только** в процессе бота. Второй экземпляр бота отправил бы каждое сообщение дважды.
- API масштабируется свободно, но держится один воркер — лимитеры (запросов и исходящего Telegram) живут в памяти процесса. Синхронизация появится с переходом на PostgreSQL + Redis при росте до 30–50k пользователей.

SQLite (WAL) на одном VPS уверенно держит 10k пользователей; схема написана переносимо — при росте меняется только слой сессии.

## Деплой

```bash
docker compose -f infra/docker-compose.yml up -d --build
```

В комплекте:

- **бот + API** (Dockerfile);
- **Caddy** — автоматический https, домен впиши в `infra/Caddyfile` и в `.env` → `WEBAPP_URL`;
- **healthcheck** бота и API — зависший контейнер перезапускается сам;
- **ежедневный бэкап** базы (`sqlite3 .backup`, хранение 14 дней).

Перед боевым запуском: `DEV_MODE=0`, свой `BOT_TOKEN`, заполненный `ADMIN_ID`, `WEBAPP_URL=https://домен`.

## Мониторинг

- **Sentry** (`SENTRY_DSN`): ловит все необработанные исключения бота и API — включается первым, без него «багов нет» просто не видно.
- **UptimeRobot** мониторит внешний `https://домен/api/health`.
- **Алерты**: падение процесса (контейнер перезапущен), рост 5xx > 1% за 5 минут, backlog рассылок, доля фолбэков/офлайна LLM и средняя латентность, диск > 80%, размер бэкапов.
- **Логи**: `docker logs` с ротацией (json-file). На старте этого достаточно.

## Бэкапы

- Локальный `.backup` ежедневно (compose, 14 дней).
- **Off-site**: выгрузка на S3-совместимое хранилище или второй VPS — локального бэкапа мало для персональных данных.
- **Проверка восстановления** раз в месяц: восстановить бэкап в пустую БД, прогнать `PRAGMA integrity_check` + selfcheck. Непроверенный бэкап — это отсутствие бэкапа.

## CI/CD

GitHub Actions: lint (ruff), pytest + selfcheck на каждый PR, сборка Docker, метки на теги → деплой на VPS по SSH.

- **Staging**: отдельный инстанс (та же compose) с тестовым ботом-дубликатом и `DEV_MODE=1`. На нём — ручные проверки и нагрузочные прогоны.
- **Релизная дисциплина**: заморозка деплоев за 48 ч до запуска; деплой утром в рабочий день; откат = `docker compose` на предыдущий тегированный образ.

## Запуск (runbook)

1. **За 48 ч**: заморозка деплоев. Проверить конфиг на боевом: `DEV_MODE=0`, `BOT_TOKEN`, `ADMIN_ID`, `WEBAPP_URL`, LLM-ключи, `PADDLE_WEBHOOK_SECRET` (если включаем). `selfcheck` на сервере — все ✅.
2. **За 24 ч**: ручной тест-план на staging (онбординг, оплата Stars и Paddle, рассылка на себя), тестовая оплата, бэкап проверен восстановлением.
3. **За 2 ч**: включить мониторинг (Sentry, алерты), проверить логи, снять снапшот размеров БД.
4. **День X**: маркетинг по плану (`docs/MARKETING.md`). Наблюдать: Sentry (рост ошибок — фикс/откат по протоколу), планировщик (уложился ли утренний тик), LLM (фолбэки, себестоимость, 429), БД (размер, `database is locked`).
5. **При проблеме**: уведомить в админ-чат, применить откат на предыдущий образ, НЕ держать систему в полурабочем состоянии. Проблема → задача в бэклог → фикс после стабилизации.

## Целевые SLO

- Ответ бота p95 < 10 с, p99 < 30 с (включая LLM-цепочку и фолбэк).
- API p95 < 400 мс, p99 < 1,5 с (кроме генераций); 5xx < 0,1%; аптайм 99,5%.
- Утренний прогноз до 09:30 по локальному времени; рассылки — каждый таргет ровно один раз, доставка за час.
- Пик 10 000 юзеров/сутки, до 4 000 DAU, до 2 000 одновременных в чате — без деградации.

## Масштабирование

- **30–50k пользователей** → PostgreSQL с репликой + Redis-лимитеры (схема переносима, меняется слой сессии и тип id).
- Перед масштабированием обязательны: off-site бэкап, пересчитанная юнит-экономика (CAC < LTV/3, LLM < 30% тарифа), нагрузочные прогоны.

## Проверки перед боевым запуском

- [ ] `DEV_MODE=0`, боевые токены, домен, https (Caddy).
- [ ] Sentry подключён, алерты настроены, off-site бэкап проверен восстановлением.
- [ ] Денежные пути идемпотентны (тест «повторный платёж не выдаёт товар дважды»).
- [ ] Рассылки без дублей; аудитория не голодает (пагинация).
- [ ] Ручной тест-план пройден на staging; runbook прочитан и понятен.
