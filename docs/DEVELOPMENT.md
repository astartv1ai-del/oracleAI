# Разработка

Техническая документация: стек, архитектура, структура репозитория, запуск, ключевые подсистемы и инженерные решения. Для понимания «как устроено и как разрабатывать». Эксплуатация (деплой, мониторинг, бэкапы) — в `docs/OPERATIONS.md`.

## Стек

- **Python 3.13+**, ~15 600 строк кода в `app/`.
- **Telegram-бот**: aiogram (FSM для онбординга, клавиатуры, инлайн-оплата за Stars).
- **API / Mini App**: FastAPI + встроенный фронтенд (HTML/CSS/JS), сервится тем же процессом.
- **БД**: SQLite (WAL), один файл, схема и миграции в `app/data/`. 40 таблиц.
- **Астрология**: Swiss Ephemeris через `kerykeion` (5.x), геокодинг `geopy`. Тяжёлые библиотеки необязательны: без них бот работает в лайт-режиме астрологии.
- **LLM**: Claude (Anthropic), OpenAI и любой OpenAI-совместимый сервер (vLLM, LM Studio, Ollama) через единый слой.
- **Инфраструктура**: Docker Compose, Caddy (авто-https), Sentry, UptimeRobot.
- **Тесты**: pytest, 250 автотестов + самопроверка `scripts/selfcheck.py`.

## Архитектура

```
Telegram  ←→  бот (aiogram)  ←→  app/services (правила)  ←→  app/repo (SQL)
                                  app/core (агенты, расчёты, безопасность)
Mini App  ←→  API (FastAPI)  ──────────────────────────────────────→  SQLite
Панель    ←→  API (admin)
Планировщик внутри процесса бота → утренние прогнозы, рассылки, гороскопы
```

Процессов **ровно два** — бот и API. Это принципиально: планировщик, утренние прогнозы и рассылки живут только в процессе бота, поэтому второй экземпляр бота недопустим (отправил бы каждое сообщение дважды). API масштабируется свободно, но держится один воркер — лимитеры in-process (см. ниже).

Слои:

- `app/bot/` — aiogram: онбординг, чаты, Таро, практики, профиль, оплата.
- `app/core/` — агенты (`agents/specs.py`, `agents/runtime.py`), расчёты (`astro.py`, `tarot.py`, `matrix.py`), память (`memory.py`), скиллы (`skills.py`), безопасность (`safety.py`, `flood.py`), персоны (`personas.py`), устойчивый сид (`stable.py`).
- `app/api/` — FastAPI: роутеры `today`, `chat`, `tarot`, `chart`, `practices`, `diary`, `shop`, `share`, `profile`, `admin`, `webhooks`, аутентификация по подписи Telegram.
- `app/services/` — правила продукта: `billing` (оплата/выдача), `limits`, `chat`, `practices`, `horoscopes`, `broadcast`, `referrals`, `invoices`, `scheduler`, `telegram`, `analytics`.
- `app/repo/` — SQL-слой (users, payments, orders, plans, products, content, memory, events…).
- `app/data/` — схема и миграции, сид каталога (`seed.py`).
- `app/pdfgen/` — генератор PDF-разборов.
- `admin/` — админ-панель (статический фронтенд к `/api/admin`).
- `web/` — публичный лендинг, `robots.txt`, `sitemap.xml`.
- `scripts/` — `selfcheck`, генерация промокодов и PDF, healthcheck, seed.
- `tests/` — pytest-наборы по подсистемам.
- `infra/` — Dockerfile, docker-compose, Caddyfile.
- `load/` — нагрузочные скрипты (locust, simulate).

## Быстрый старт

```bash
cd oracle
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # вписать BOT_TOKEN, ADMIN_ID, WEBAPP_URL
python -m app.bot.main        # бот
uvicorn app.api.main:app --port 8080   # API / Mini App
```

Бот работает сразу:

- **без ключей** — офлайн-режим: шаблонные мистические трактовки на реальных данных карты, Таро и Матрицы;
- **с ключом Claude или OpenAI** (любым) — полный агентный режим.

Проверка проекта одной командой: `python -m scripts.selfcheck`.

Локальный просмотр Mini App: `http://localhost:8080/?dev_user=<твой_tg_id>` при `DEV_MODE=1`.

## LLM-слой

Провайдеры (`LLM_PROVIDER=auto`) выстраиваются в **цепочку отказоустойчивости**: `custom → anthropic → openai`. Упал основной — агент сам уходит на резервный; в конце — офлайн-режим. `CUSTOM_LLM_BASE_URL` подключает любой OpenAI-совместимый сервер.

Ключевые решения слоя:

- **Потоковый ответ обязателен** для OpenAI-совместимых серверов (`stream=True`): многие прокси и локальные раннеры отвечают SSE независимо от запроса, и при обычном разборе `content` приходит пустым.
- Размышления reasoning-моделей (`reasoning_content`) в ответ не попадают.
- Если модель не умеет tool-use, включается pre-tool режим: скиллы выполняются заранее и подкладываются в контекст.
- **Защита от всплеска**: семафор + rate-limit на вызовы (настраивается), чтобы сотни корутин не били в API одновременно (иначе 429-шторм и мгновенный уход в офлайн).
- **Таймауты**: на вызов и общий бюджет времени на запрос — мёртвый провайдер не держит ответ минутами.
- **Учёт себестоимости**: каждый вызов пишет `cost_usd` по `purpose` (answer/forecast/memory/horoscope) — это база юнит-экономики в `docs/MONETIZATION.md`.

## Память

`app/core/memory.py` — долгая память: факты дедуплицируются **по смыслу**, ищутся под текущий вопрос и собираются в сводку. Поиск по словам; при флаге `semantic_memory` — по эмбеддингам. Глубина памяти зависит от тарифа.

## Безопасность

- **Кризисный протокол** (`core/safety.py`): сообщения о суициде, самоповреждении и насилии не доходят до модели — решение принимает код, а не промпт. Пользовательница получает поддержку и контакты помощи, лимит не тратится. Контакты правятся в панели (`safety.helplines`, по странам).
- **Антифлуд и лимиты**: rate-limiter исходящих Telegram (`core/flood.py`), дроссель запросов, лимиты вопросов по тарифу (атомарно для денежных путей).
- **Подпись Telegram initData** проверяется со сроком жизни 24 часа.
- **Вебхуки платёжек**: подпись по сырому телу + журнал `webhook_events` — повторная доставка никогда не выдаёт товар дважды (идемпотентность).
- **Деньги атомарны**: оплата → выдача в одной транзакции; повторный платёж не начисляет дни дважды.
- **Удаление данных**: `/delete_me` анонимизирует аккаунт (имя, дату рождения, карту, дневник, память, переписку); финансовый след остаётся по закону.
- **Устойчивый сид** (`core/stable.py`): встроенный `hash()` рандомизируется при каждом запуске Python — из-за этого карта дня и балл пары менялись после рестарта. Сид зафиксирован.
- `DEV_MODE=1` пускает в API любого по `?dev_user=<id>` без подписи — на боевом сервере флаг выключен.

## Нагрузка и масштабирование

Проект проектировался под запуск с наплывом порядка 10 000 пользователей. Ориентиры:

- p95 ответа бота < 10 с, p99 < 30 с (включая LLM-цепочку и фолбэк).
- API (Mini App) p95 < 400 мс, p99 < 1,5 с, кроме генераций.
- Ошибки 5xx < 0,1%; ноль ошибок в денежных путях; аптайм 99,5%.
- Утренний прогноз до 09:30 по локальному времени пользователя.
- Рассылки: каждый таргет ровно один раз, вся доставка за час от слота.

Инженерные решения под эти цели:

- **Параллельная генерация** утренних прогнозов (семафор, предгенерация ночью, офлайн-шаблон при перегрузке) — последовательный проход по тысячам пользователей не укладывался бы в окно.
- **Пагинация аудитории** в рассылках (`ORDER BY tg_id`) — без неё хвост таймзоны никогда не получает прогноз.
- **Сериализация миграций на старте** — бот и API стартуют вместе, иначе второй процесс падает на втором `ALTER`.
- **Один воркер API**: лимитеры (rate-limit запросов, бакет Telegram) живут в памяти процесса; несколько воркеров дали бы каждому свой запас. Синхронизация появится вместе с переходом на PostgreSQL + Redis при росте до 30–50k пользователей.
- **Ретеншен событий** (`events`, `llm_usage`) — аналитика вне hot-path, purge 90–180 дней.

## Тесты и проверка

- `pytest tests/ -q` — 250 автотестов по подсистемам: биллинг, лимиты, рассылки, планировщик, FSM-онбординг, безопасность, PDF, LLM-фолбэк без сети, API, миграции, гонки.
- `python -m scripts.selfcheck` — синтаксис, импорты, конфиг, деньги, лимиты, кризисный протокол, PDF, LLM-проб.
- CI (GitHub Actions) — lint, pytest + selfcheck на каждый PR.
