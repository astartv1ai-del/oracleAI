# Контракты продуктовых путей: синастрия и транзиты

Статус документа: **реализуется в текущей итерации** (26 августа 2026). Документ фиксирует отдельные JSON-контракты для новых путей, не изменяя уже действующий контракт полной натальной карты.

## Границы текущего релиза

В этом релизе включаются два независимых продуктовых пути:

| Путь | Вход | Расчёт | Что возвращается | Чего пока нет |
|---|---|---|---|---|
| `synastry` | сохранённый партнёр владельца аккаунта | межкартные мажорные аспекты по активным планетам | положения обеих карт, аспекты, точность и причины недоступности | новый графический круг, композитная карта, прогноз событий |
| `transits` | сохранённая карта владельца + явный `as_of` | положения транзитных активных планет и их мажорные аспекты к натальным планетам | снимок неба, аспекты к наталу, точность снимка | транзитные дома/углы, периоды входа/выхода, автоматические предсказания |

**Composite** и **returns** остаются отдельными будущими контрактами. Их нельзя выдавать через эти маршруты под другим названием.

## Общие правила

1. Каноническим источником позиций остаётся существующий `app.core.astro` на базе закреплённого Kerykeion/Swiss Ephemeris. Ручная геометрия колеса и клиентский SVG не добавляются.
2. Маршруты используют только сохранённые данные текущего владельца. Дата рождения или координаты не принимаются как способ подменить натальную карту в `GET`-URL. Синастрия ссылается на `partner_id`; транзиты используют сохранённую карту владельца.
3. Контракт возвращает числовые долготы в градусах, знак, отображаемое имя и округлённые значения для интерфейса. LLM трактует только полученное evidence и не пересчитывает его.
4. Raw SVG, исходные файлы рендера и персональные данные в image URL, кэше или логах не появляются. В первом релизе оба пути возвращают JSON без нового изображения.
5. Если исходные данные недостаточны, API возвращает структурированный ответ `422` с `code`, `message` и `missing`, а не правдоподобный результат с выдуманными домами или углами.

## Контракт `synastry_schema_version = 1`

### Запрос

```json
{
  "partner_id": 42
}
```

`partner_id` должен принадлежать текущему Telegram-пользователю. Не принадлежащий владельцу или отсутствующий партнёр не раскрывается наружу отдельным статусом; маршрут отвечает единым `404`.

### Успешный ответ

```json
{
  "synastry_schema_version": 1,
  "product": "synastry",
  "precision": "exact",
  "person": {
    "role": "owner",
    "label": "Я",
    "chart_precision": "exact",
    "planets": []
  },
  "partner": {
    "role": "partner",
    "partner_id": 42,
    "label": "Имя партнёра",
    "chart_precision": "exact",
    "planets": []
  },
  "aspects": [
    {
      "p1": "Sun",
      "p1_label": "Солнце",
      "p2": "Moon",
      "p2_label": "Луна",
      "code": "trine",
      "label": "трин",
      "glyph": "△",
      "orb_deg": 1.2
    }
  ],
  "limitations": [
    "В первом релизе показываются мажорные межпланетные аспекты; дома партнёров и композит не строятся."
  ]
}
```

В синастрии разрешены только две сохранённые **точные** карты с планетными долготами. Если у владельца или партнёра `precision != exact`, результат не строится: `422` с `code = exact_charts_required`, `missing = ["owner"]` и/или `missing = ["partner"]`. Это предотвращает смешивание точной карты с датой без времени и ложные заявления об углах.

## Контракт `transit_schema_version = 1`

### Запрос

```json
{
  "as_of": "2026-08-26",
  "time": "12:00"
}
```

`as_of` обязателен и принимает ISO-дату `YYYY-MM-DD`. Поле `time` необязательно и принимает локально независимое UTC-время `HH:MM`. Если `time` не передан, расчёт выполняется на детерминированном дневном срезе `12:00 UTC` и получает `precision = day`; при переданном времени получает `precision = instant`. Это честно отражает, что без времени внутри даты Луна и быстрые точки не имеют единственного положения.

Транзитная позиция рассчитывается на нейтральной геометрии `0°/0°`, `UTC`; в первом контракте она используется только для геоцентрических долгот планет. Транзитные дома, ASC, MC и другие локальные углы намеренно не возвращаются. Натальная карта владельца может быть `exact` или `date_only`: для транзитов нужны сохранённые натальные планетные долготы, но в ответе явно указывается `natal_precision`.

### Успешный ответ

```json
{
  "transit_schema_version": 1,
  "product": "transits",
  "as_of": "2026-08-26",
  "sampled_at": "2026-08-26T12:00:00+00:00",
  "precision": "day",
  "natal_precision": "exact",
  "transit_planets": [],
  "aspects_to_natal": [
    {
      "transit": "Saturn",
      "transit_label": "Сатурн",
      "natal": "Sun",
      "natal_label": "Солнце",
      "code": "square",
      "label": "квадрат",
      "glyph": "□",
      "orb_deg": 2.4
    }
  ],
  "limitations": [
    "Дневной срез не является точным временем положения Луны.",
    "Транзитные дома и углы в этом контракте не строятся."
  ]
}
```

Аспекты используют ту же явную политику мажорных аспектов и орбов, что и каноническая натальная карта. Одноимённые транзитная и натальная точки не образуют отдельный межкартный аспект. В первом релизе список транзитных точек ограничен десятью традиционными планетами; узлы, дополнительные точки и углы не включаются в межкартные аспекты.

## Ошибки и недоступность

Все ошибки продукта имеют JSON-форму:

```json
{
  "detail": {
    "code": "exact_charts_required",
    "message": "Для синастрии нужны две точные карты.",
    "missing": ["partner"]
  }
}
```

Коды стабильны внутри версии: `chart_required`, `exact_charts_required`, `partner_not_found`, `invalid_as_of`, `invalid_time`, `calculation_unavailable`. Тексты могут локализоваться, но `code` используется Mini App и тестами.

## Совместимость с текущей натальной картой

Текущий `natal_schema_version = 2` сохраняется без изменения. Полная точная натальная карта по-прежнему включает 10 традиционных планет, 12 домов, ASC/MC, Rahu/Ketu, Lilith, Chiron/Juno/Ceres/Vesta/Pallas, мажорные аспекты и ретроградность. При неизвестном времени сохраняются ограничения `date_only`: дома и углы не выдаются и колесо не строится.

## Будущие отдельные контракты

`composite_schema_version` и `returns_schema_version` будут добавлены только отдельными задачами с собственными входами, precision-gate, тестовыми фикстурами и UX. Нельзя считать их включёнными только потому, что синастрия или транзиты уже доступны.
